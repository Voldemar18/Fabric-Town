# Fabric Town — симулятор логистики города
ps:эта игра раскрывает по большей части разные виды алгоритмов и их практическое применение)
## 1. Что решает проект

**Fabric Town** — пошаговый (в реальном времени) симулятор-песочница, в котором игрок строит город и управляет логистикой между **фабриками**, **магазинами** и **домами**:

* фабрики производят один тип товара с заданной скоростью,
* машины-курьеры развозят товар от фабрик к магазинам по **односторонним дорогам**,
* жители домов ходят в магазины за случайным товаром,
* игрок строит/сносит дороги и здания, покупает новые участки карты, зарабатывает деньги на продажах.

Ключевая алгоритмическая часть — **маршрутизация машин** по графу дорог с учётом одностороннего движения и запрета разворота на 180°, а также **динамическая перестройка маршрутов** при изменении дорожной сети игроком.

Проект — итоговая работа по дисциплине «Практикум по алгоритмам».

Проект разделён на пакеты по смысловым областям:
````
ru.student.fabricTown

├── buildings/ — здания: Building, Factory, Shop, House, Road, RoadShape, BuildingSize

├── logic/ — алгоритмы: GraphBuilder, PathFinder, Dispatcher,PlacementRules, RoadRegistry, Blueprint, Catalog,BuildingFactory, GameEvents

└── visualization/ — Swing UI: GameFrame, GamePanel, Renderer, Camera,HudPanel, BuildPanel, ShopPanel, RouteOverlay,NotificationRenderer, BuildMode
````

**Ключевые классы:**

| Класс | Ответственность |
|---|---|
| `Game` | Тик симуляции, строительство/снос, привязка фабрик к магазинам, перестройка маршрутов |
| `GraphBuilder` | Построение графа дорог (списки смежности, направленные рёбра) |
| `PathFinder` | Поиск кратчайшего пути (Дейкстра) |

| `Shop` | Склад, продажа, лимит фабрик **по типу товара** |
| `Factory` | Производство, склад, грузоподъёмность машины, лимит магазинов |

## 3. Структуры данных и алгоритмы

### 3.1. Граф дорог — **списки смежности**

**Где:** `GraphBuilder.adjacency` — `Map<Point, List<Edge>>`.

**Что:** вершина графа — клетка с дорогой. Ребро — переход между соседними дорогами с учётом:
1. направления дороги (одностороннее движение),
2. запрета разворота на 180° (переход разрешён только «вперёд» — прямо или на 90°).

**Обоснование выбора:** см. раздел 5.

### 3.2. Поиск пути — **алгоритм Дейкстры**

**Где:** `PathFinder.findPath(Point start, Point goal)`.

**Как:** классическая Дейкстра с `PriorityQueue<Point>` и `Comparator.comparingDouble(p -> dist.get(p))`. Все рёбра имеют вес 1, но алгоритм готов к разным весам (см. ТЗ, п. 5 «Альтернативы»).

**Сложность:** `O((V + E) log V)`, где `V` — число дорожных клеток, `E` — число переходов (`E ≤ 4V`).

### 3.3. Обходы графа — **BFS**

**Где:** `GraphBuilder.isReachable`, `GraphBuilder.reachableFrom`, `GraphBuilder.findNearestShop`, `GraphBuilder.isWeaklyConnected`, `GraphBuilder.findIsolatedRoads`.

**Сложность:** `O(V + E)`.

### 3.4. Хеш-таблицы

| Структура | Назначение |
|---|---|
| `GameMap.buildings : Map<Point, Building>` | доступ к объекту по координате за O(1) |
| `GameMap.roads : Map<Point, Road>` | быстрая проверка «есть ли дорога» |
| `Dispatcher.shopToFactories : Map<Shop, List<Factory>>` | привязки магазин→фабрики |
| `Dispatcher.routesToShop / routesToFactory : Map<Shop, Map<Factory, List<Point>>>` | пути туда/обратно |
| `Shop.storage : Map<Product, Integer>` (EnumMap) | склад магазина |
| `NotificationCenter.byTag : Map<String, Notification>` | дедупликация уведомлений |
| `RoadRegistry.occupied : Set<Point>` | реестр занятых клеток |

### 3.5. Очереди и приоритетные очереди

| Структура | Где | Назначение |
|---|---|---|
| `PriorityQueue<Point>` | `PathFinder` | извлечение минимума в Дейкстре |
| `PriorityQueue<Event>` | `EventQueue` | очередь событий по времени |
| `ArrayDeque<Point>` | `GraphBuilder` (BFS) | обход в ширину |
| `ArrayDeque<Product>` | `Factory.storage` | стек склада (LIFO) |

### 3.6. Сортировки

| Где | Что сортируется | Компаратор |
|---|---|---|
| `Game.autoBindAllFactories` | магазины по расстоянию до фабрики | `Math.hypot(dx, dy)` |
| `Game.autoBindShopManual` | фабрики по расстоянию до магазина | `Math.hypot(dx, dy)` |
| `EventQueue.update` (внутри `PriorityQueue`) | события по времени, при равенстве — по `sequence` (FIFO) | `Event.compareTo` |
| `NotificationCenter.getVisible` | уведомления по id (новые сверху) | `Long.compare` |

### 3.7. Жадные алгоритмы

| Где | Жадный выбор | Обоснование корректности |
|---|---|---|
| `Game.tryAutoBindFactory` | ближайший свободный магазин | минимизирует время доставки → максимизирует пропускную способность |
| `Person.ShopFinder` (в `Game.findAlternativeShop`) | ближайший магазин с нужным товаром | по ТЗ: «идёт в ближайший доступный магазин» |

### 3.8. Прочие техники

| Техника | Где | Назначение |
|---|---|---|
| **Линейная интерполяция** | `Car.advance`, `Camera.update` | плавное движение между клетками |
| **Брезенхэм** | `GamePanel.paintLine` | рисование линии дорог/сноса мышью |
| **State Machine** | `Car.State`, `Person.State` | управление поведением агентов |
| **Дедупликация по тегу** | `NotificationCenter.byTag` | не спамить одинаковыми сообщениями |
| **Двусторонние маршруты** | `Dispatcher` | корректная работа с односторонними дорогами |

## 4. Сложность

### По времени

| Операция | Сложность | Комментарий |
|---|---|---|
| `GameMap.place/remove` | `O(w × h)` | по площади здания (1–9 клеток) |
| `GraphBuilder.rebuild` | `O(V + E)` | полная пересборка графа |
| `GraphBuilder.updateVertex` | `O(deg(p))` | точечно, после постройки/сноса |
| `PathFinder.findPath` | `O((V + E) log V)` | Дейкстра |
| `Dispatcher.bind` | `O((V + E) log V)` | два вызова Дейкстры (туда и обратно) |
| `Game.rebuildAllRoutes` | `O(B × (V + E) log V)` | `B` — число привязок фабрика↔магазин |
| `Game.tick` | `O(F + C + H + P)` | производство, машины, дома, люди |
| `Car.advance` | `O(1)` на тик | амортизированно, через `pathIndex` |
| `GraphBuilder.isReachable` | `O(V + E)` | BFS |
| `NotificationCenter.push` | `O(1)` в среднем | хеш-таблица по тегу |

**Узкое место:** `Game.rebuildAllRoutes` — при большом числе привязок и частых изменениях дорог. Вызывается при **каждой** построенной/снесённой/повёрнутой дороге. При рисовании линии из 20 клеток — 20 полных пересчётов. На карте 100×100 с 50 привязками это заметно.

### По памяти

| Структура | Сложность | Комментарий |
|---|---|---|
| `GameMap.buildings` | `O(S)` | `S` — суммарная площадь зданий |
| `GraphBuilder.adjacency` | `O(V + E)` | `E ≤ 4V` |
| `Dispatcher` маршруты | `O(B × L̄)` | `L̄` — средняя длина маршрута |
| `EventQueue` | `O(N)` | `N` — число запланированных событий |
| `RoadRegistry.occupied` | `O(C_active)` | число одновременно активных машин |

**Итого по памяти:** доминирует `Dispatcher` — `O(B × L̄)`. При `B = 50` и `L̄ = 100` это ~5000 точек.

## 5. Значимое архитектурное решение

### 5.1. Почему **списки смежности**, а не матрица смежности

**Контекст.** Карта — сетка клеток. Дороги — подмножество клеток. Размер карты может расти при покупке участков (`Game.tryBuyLand`).

**Альтернатива 1 — матрица смежности `N × N`.**

* **Плюс:** `O(1)` проверка «есть ли ребро между `u` и `v`».
* **Минус:** память `O(N²)`. При `N = 10 000` (карта 100×100) это `10⁸` ячеек — сотни мегабайт. При `N = 40 000` (200×200) — уже гигабайты.
* **Минус:** обход всех соседей — `O(N)`, а не `O(deg(v))`, что критично для Дейкстры и BFS.

**Альтернатива 2 — список рёбер `List<Edge>`.**

* **Плюс:** компактно.
* **Минус:** поиск соседей вершины — `O(E)` на каждый вызов.

**Выбор: списки смежности `Map<Point, List<Edge>>`.**

* Память `O(V + E)`, где `E ≤ 4V` (каждая дорога имеет максимум 4 выхода).
* Обход соседей — `O(deg(v))`, что даёт Дейкстру за `O((V + E) log V)`.
* Карта разреженная: доля дорог от всех клеток мала (обычно < 30%), поэтому матрица неоправданно расточительна.
* `HashMap<Point, List<Edge>>` даёт `O(1)` доступ к вершине.

### 5.2. Почему **два независимых маршрута**, а не реверс одного

**Контекст.** Дороги **односторонние**. Машина едет от фабрики к магазину по одному пути, обратно — по другому.

**Альтернатива — `Collections.reverse(pathToShop)`.**

* **Плюс:** одна Дейкстра вместо двух, `O((V + E) log V)` вместо `O(2 (V + E) log V)`.
* **Минус:** **некорректно**. Обратный путь нарушает направления дорог: если `A → B` — односторонняя, то путь `B → A` по реверсу недопустим.

**Выбор: два независимых вызова Дейкстры — `findPath(factoryExit, shopExit)` и `findPath(shopExit, factoryExit)`.**

* Корректность важнее двукратного времени построения маршрута.
* Маршрут строится **один раз** при привязке (или при изменении дорог), а не каждый тик, поэтому `O(2 (V + E) log V)` амортизируется.

### 5.3. Почему **EventQueue не интегрирована в Game.tick** (честно)

`EventQueue` реализована как полноценная структура (приоритетная очередь по времени, дедупликация, периодические события), но в текущей версии `Game.tick(double dt)` использует **прямые таймеры**:

* `Factory.productionProgress`,
* `House.exitTimers`,
* `Car.unloadTimer`,
* `Person.shopTimer`.

**Причина:** на текущем объёме (десятки объектов) разница в производительности незаметна, а прямая тик-система проще для отладки. **EventQueue** — задел на будущее развитие: при росте числа объектов (тысячи) она даст выигрыш за счёт пропуска «пустых» тиков для неактивных объектов и естественной поддержки асинхронности.

## 6. Альтернативные подходы, которые были рассмотрены

| Задача | Реализовано | Альтернатива | Почему отклонена |
|---|---|---|---|
| Хранение графа | списки смежности | матрица смежности | память `O(N²)` — карта разреженная (см. 5.1) |
| Поиск пути | Дейкстра | BFS | у дорог могут быть разные веса (в будущем — износ, стоимость); Дейкстра универсальнее |
| Поиск пути | Дейкстра | A* | эвристика Манхэттена на малой карте даёт малый выигрыш, а код усложняет; на больших картах — стоит рассмотреть |
| Обратный маршрут | отдельный Дейкстра | `Collections.reverse` | некорректно для односторонних дорог (см. 5.2) |
| Связь фабрика↔магазин | фиксируется заранее при bind | поиск пути каждый рейс | поиск пути `O((V+E) log V)` на каждый рейс — дорого; фиксация позволяет сразу сообщить об ошибке |
| Ходьба людей | по прямой | по графу дорог | архитектурное упрощение; второй поиск пути на каждого человека замедлил бы симуляцию |
| Асинхронность | тик-система (`Game.tick`) | EventQueue | `EventQueue` реализована, но не интегрирована — см. 5.3 |
| Загрузка машины | пачка `min(capacity, freeSpace)` | задача о рюкзаке | все товары одного типа и одинакового «веса» 1 — рюкзак вырождается в `min` |
| Распределение машин | жадный (ближайший магазин) | DP / линейное программирование | жадный корректен и быстр; DP избыточен при текущих ограничениях |

## 7. Пограничные случаи

Покрыты тестами (см. `src/test/java/...`) и демонстрируются на защите:

| Случай | Где обрабатывается | Поведение |
|---|---|---|
| Пустая карта (нет дорог) | `PathFinder.findPath` | возвращает `null` |
| `start == goal` | `PathFinder.findPath` | возвращает `[start]` |
| `start` не в графе | `PathFinder.findPath` | возвращает `null` |
| Дорога-тупик | `GraphBuilder.buildEdgesFrom` | 0 исходящих рёбер |
| Запрет разворота на 180° | `GraphBuilder.buildEdgesFrom` | ребро не добавляется |
| Магазин полон | `Car.tryStartDelivery` | машина → `BLOCKED` |
| Склад фабрики пуст | `Car.tryStartDelivery` | `false`, ждём следующего тика |
| Дорога снесена под машиной | `Game.rebuildAllRoutes` → `Car.markNoRoute` | машина → `NO_ROUTE`, ждёт |
| Дорога восстановлена | `Game.rebuildAllRoutes` → `Car.updateRoutes` | машина возрождается в ту же сторону |
| Дом без магазинов | `Game.tick` | `Person` не создаётся, warning в HUD |
| Товар отсутствует во всех магазинах | `Person.trySwitchShop` | `Person` → `RETURNING`, `missingProduct` |
| Переполнение склада магазина | `Shop.addProducts` | останавливается на границе capacity |
| Переполнение склада фабрики | `Factory.tick` | производство пауза |

## 8. Как запустить

### Требования
* JDK 17+ (используются `switch`-выражения, `record`-подобные конструкции, `instanceof` pattern matching)
* Maven 3.8+ (или просто `javac`)

### Сборка и запуск

```bash
mvn clean compile
mvn exec:java -Dexec.mainClass="ru.student.fabricTown.visualization.GameFrame"
```
